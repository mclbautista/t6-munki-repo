== 7. What is still NOT verified, stated exactly ==

1. **Whether the repository is reachable from the public internet.** Unverified by us. What stands
   behind the claim is (a) the NAS establishing no path (verified, section 6) and (b) no hand-made
   port-forward on the device providing the fleet LAN's uplink — which cannot be read from here: it
   answers on none of the ten ports probed, and its MAC block has no vendor name in the registry. The
   specific check is a UI fact: the port-forwarding / virtual-server table of that uplink device, where
   a forward of TCP 80 to 192.168.88.188 would be visible.
2. **The path of any client whose primary connection is Wi-Fi.** `201 Bay 03 M1 Ultra`
   (192.168.254.106 in the inventory) is on a subnet nothing here routes to, and the fleet's SSH probe
   cannot reach it either (ticket 05's standing gap). Its ability to fetch the repository is therefore
   unknown, and 13B named exactly this as a defect to fix rather than a hole to allowlist.
3. **Whether the Wi-Fi path refusal generalizes.** This host's Wi-Fi interface cannot reach the
   endpoint (section 1), which is one real refusal from a non-fleet path. Whether every device on that
   network is likewise cut off follows from the topology, not from a test run per device.
