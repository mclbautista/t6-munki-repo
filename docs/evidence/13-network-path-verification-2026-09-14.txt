** This is the second capture. ** The first, committed in 26df1cd, was reviewed line by line against
its own claims and three defects were found and corrected here:

 1. It recorded the fleet LAN's gateway as a device that "answers on TCP 53 only". That is false: port
    80 answers with a 301 to its own management UI, which is a pfSense login page (section 4). The
    consequence matters more than the error — the port-forward table is blocked by *credentials*, not
    by unreachability, so the remaining check is one Cyril can unblock, not one that "cannot be made".
 2. Its routing capture was truncated with `head -8`, so the route that makes the fleet path work and
    the absence of a route to 192.168.254.0/24 were both asserted without a command that shows them.
    Section 2 now captures the table untruncated and counts the missing route.
 3. Its connection-log extraction grepped for the prefix `192.168.88.`, which cannot detect an address
    outside that subnet — the output was true by construction. Section 6 extracts addresses without a
    prefix bias and shows what that turns up, including values that are artifacts of regexing a binary
    log.

A fourth claim was corrected in the ticket and the ADR rather than here: a TCP timeout was written as a
"refusal". A timeout is no response at all (curl exit 28), which is also what a filtered or
black-holed connection looks like, so it is recorded as a timeout.

Ticket 13 asks for the repository to be reachable only from T6's own network path. Decisions 13A-13D
replaced the originally-imagined NAS firewall with network segregation, so the remaining questions are
facts about paths: from where can the endpoint be reached, what did the NAS itself establish, and what
is still unknown.

Method: read-only. Local checks run on Cyril's Mac mini; NAS facts come from QNAP MCP read calls and the
`t6-nas` SSH alias, whose filesystem is read-only for this user. No configuration was changed anywhere;
nothing on the NAS, a Mac, or a client was written to.

The two public addresses named below are T6's own uplinks, and the port checks are against T6's own
gateway device only.

== 7. What is still NOT verified, stated exactly ==

1. **Whether the repository is reachable from the public internet.** Unverified by us. What stands
   behind the claim is (a) the NAS establishing no path of its own (section 6, verified) and (b) the
   configuration of the fleet LAN's pfSense firewall — in particular its port-forward / NAT table — which
   is only readable with credentials (section 4 shows the UI, not its contents).
2. **Whether the ISP address is public or carrier-shared.** Gate-side and unverified, as ticket 13D
   recorded. Section 3 shows this host's *egress* address on each path; it does not show how many NATs
   are between this host and the internet, and a carrier-shared address would mean a forward could not
   be reached even if one existed. Nothing here distinguishes the two.
3. **The path of any client whose primary connection is Wi-Fi.** `201 Bay 03 M1 Ultra`
   (192.168.254.106 in the inventory) is on a subnet this host has no route to (section 2), and the
   fleet's SSH probe cannot reach it either (ticket 05's standing gap). Its ability to fetch the
   repository is unknown; 13B named exactly this as a defect to fix rather than a hole to allowlist.
4. **Whether the Wi-Fi timeout generalizes.** One host's Wi-Fi interface got no reply (section 1).
   Whether every device on that network is likewise cut off follows from the topology, not from a test
   per device — and a timeout is not proof of unreachability in any case.
