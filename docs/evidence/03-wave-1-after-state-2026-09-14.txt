1. KEY AUTHENTICATION, PER MACHINE (the form that is required, and why)
--------------------------------------------------------------------------------
The collector's own ssh argv carries no identity flag - it is

    ssh -o BatchMode=yes -o ControlMaster=auto -o ControlPath=/tmp/munki-fleet-<host>.sock \
        -o ControlPersist=120s <host> <command>

(read from munki_fleet/targets.py:149-161), so a destination only works if the collector host's
~/.ssh/config supplies User/IdentityFile/IdentitiesOnly for it. The fleet key is not a default
identity name, so plain `ssh t6@<ip>` cannot work by design; every measured line below either names
the key explicitly or goes through a stanza.

    $ ssh -n -o BatchMode=yes -o ConnectTimeout=8 -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_t6 \
          -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null t6@<ip> '<identity read>'

Evidence for 202B-Mac-Studio is the same four absences, with /usr/local holding only bin/lib/sbin.

Both machines DO have manifests in the repository - manifests/202-Mac-Pro-3 (358 bytes) and
manifests/202B-Mac-Studio (366 bytes), published 2026-09-13. A manifest for a machine with no Munki
client is a manifest nothing reads: it was authored ahead of enrolment, which is a legitimate order
of work, but it means the repository's picture of the fleet (manifest per machine) is not evidence
that a machine is a client.

What this changes, stated plainly:
    - These two machines cannot be observed for Munki client state, now or after their access is
      fixed, because there is no client state to observe. The observation outcome is `partial /
      no-munki-tools` and that is the correct reading.
    - The first-wave rollout tickets (16, 17) assume a managed client exists on the wave's machines.
      For 202-Mac-Pro-3 and 202B-Mac-Studio that assumption is false today, so wave 1's real
      prerequisite for them is **enrolment**, which is a bigger and more privileged change than ssh
      access and needs its own decision. It is not attempted here.
    - Ticket 06's criterion that every inventoried Mac resolves its own machine manifest cannot be
      satisfied on a machine with no client, so some of its unticked criteria are gated on enrolment
      rather than on access. That re-scoping is recorded, not acted on, in this ticket.
    - The reverse is also now answerable: SSH access is what makes "which Macs are actually enrolled"
      a measurable question for the fleet instead of an assumption. Two of the three wave machines
      answered it with a flat no.


7. 202A MAC MINI M4 (192.168.88.175): WHY IT IS STILL OUT
--------------------------------------------------------------------------------
Measured, not inferred. sshd is up and serving three host keys (ssh-keyscan answered from
192.168.88.175), so the service is fine. Authentication fails:

    t6@192.168.88.175: Permission denied (publickey,password,keyboard-interactive)

and therefore the served host key could not be checked against the machine's own, so no known_hosts
entry was written for it and the run reports `unreachable: Host key verification failed.` rather than
`authentication refused`. That ordering is honest groundwork, not a defect: host-key verification
happens before authentication, and the underlying blocker is the machine-side authorization.

The key Cyril authorized on the other two machines did not take here. What can be established from
outside is exhausted: sshd answers, and sshd cannot tell an observer whether an account exists, so
"no such key" and "no such account" are indistinguishable from the collector. The checks that
distinguish them have to run at the machine:

    whoami
    dscl . -list /Users | grep -v '^_' | sort
    ls -ld /Users/* | head -20
    ls -la ~t6/.ssh
    ssh-keygen -lf ~t6/.ssh/authorized_keys
    stat -f '%Su %Sp %N' ~t6/.ssh ~t6/.ssh/authorized_keys

The two failure modes worth checking first, both of which the runbook named before the work started:
a different account name on this machine, in which case `~t6` expanded to a home no account owns and
the key landed where nothing reads it; or the file or its directory ending up owned by root or wrong
in mode, which sshd's StrictModes refuses silently as `Permission denied`.
