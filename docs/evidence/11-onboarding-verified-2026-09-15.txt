**One deliberate asymmetry, explained rather than reported as a mismatch.** The evidence block each
operator sees says `launchd munki jobs : 6`; a read-back as an ordinary user reports **3**. Both are
true: `ls /Library/LaunchDaemons/com.googlecode.munki.*.plist | wc -l` is 6 (that is the

the check, not the machine: a count whose answer depends on the privilege of the shell that ran it
must say which context it counted in.

    "SoftwareRepoURL" => "http://192.168.88.188/MunkiRepo"
    "UseClientCertificate" => 0

`ClientIdentifier` is present as an **empty string**, and that is not something this procedure wrote.
It is Munki's own default, in the tools' own source:

    $ ssh 202-Mac-Pro-3 "grep -rn 'ClientIdentifier' /usr/local/munki/munkilib/*.py | head"
    /usr/local/munki/munkilib/prefs.py:61:    'ClientIdentifier': '',

So the honest statement of what was done is: **the procedure sets no `ClientIdentifier`, and deletes a
NON-EMPTY one if it finds it** — a non-empty value is what overrides short-hostname resolution, and
that is exactly the live defect on Cyril's Mac mini (`t6-test-client`, ticket 07's outstanding item).
An empty value does not override anything, and the machine's resolved manifest is the proof.

This is worth stating in the evidence because the pasted block says "none set" while a literal reader
of the plist sees the key present. Both are true, and the difference is the sort of thing that gets
reported as a defect by whoever reads it next without the citation above. The script's own evidence
line was corrected to say this precisely, and the corrected script was re-staged on all three
machines (sha256 of the staged copy matches this host's copy byte for byte).
